# 知识库文件处理状态展示：改动交接

## 任务

请实现知识库文件列表的状态展示：文件合并成功只表示“上传完成”，解析和向量化完成后才显示“处理完成”。页面要能自动获取后续状态，并在刷新后显示正确结果。本次只改文件状态相关链路，不涉及权限系统。

## 当前实现与问题

- 后端 `FileUpload.status`：`0` 上传中、`1` 上传完成。`FileUpload.parseStatus`：`null/0` 待处理、`1` 处理中、`2` 处理完成、`3` 本次处理异常、`4` 进入死信队列。见 `src/main/java/com/yizhaoqi/smartpai/model/FileUpload.java`。
- `GET /api/v1/documents/uploads` 已返回 `status`、`mergedAt` 等字段，但构造响应时没有返回 `parseStatus`。见 `src/main/java/com/yizhaoqi/smartpai/controller/DocumentController.java#getUserUploadedFiles`。
- 前端合并接口成功后，`frontend/src/store/modules/knowledge-base/index.ts#mergeFile` 立即把上传任务设为 `UploadStatus.Completed`。文件列表 `frontend/src/views/knowledge-base/index.vue` 据此显示“已完成”，容易让人误以为文件已经能用于检索。
- 页面 `getList()` 只在进入页面或手动刷新时调用。已有行刷新时只同步了上传 `status`，没有同步解析状态；即使接口新增字段，也要修正这段更新逻辑。
- Kafka 消费者在每次处理异常时写 `parseStatus=3` 并抛出异常；错误处理器还会重试，最终进入死信队列才写 `4`。所以 `3` 不能直接当作最终失败。见 `FileProcessingConsumer.java`、`KafkaConfig.java`、`DeadLetterConsumer.java`。

## 目标状态与文案

先判断上传是否完成，再判断处理状态。保持现有上传进度和“上传中断”逻辑；现有 `mergedAt` 非空可视为已合并的兼容判断也应保留。

| 上传状态 | `parseStatus` | 页面显示 | 是否继续自动刷新 |
| --- | --- | --- | --- |
| 未合并 | 任意 | 现有上传进度 / 上传中断 | 不因解析状态而刷新 |
| 已合并 | `null`、缺失或 `0` | 上传完成，等待处理 | 是 |
| 已合并 | `1` | 处理中 | 是 |
| 已合并 | `3` | 处理中（重试中） | 是 |
| 已合并 | `2` | 处理完成 | 否 |
| 已合并 | `4` | 处理失败 | 否 |

`parseStatus=3` 与 `4` 对用户不需要做成两种“失败”状态：重试期间仍属于处理中，只有 `4` 显示最终失败。不要把上传用的 `UploadStatus` 数值直接复用为解析状态；二者含义不同。

本次状态文案使用“处理完成”，不要写“可检索”。目前 `VectorizationService.vectorize()` 在没有文本块时会正常返回，消费者仍可能写入 `parseStatus=2`；另外，索引写入完成与搜索立即可见也不是同一个判断。若将来要承诺“可检索”，需要另行定义并验证可检索条件。

## 建议改动位置

1. **后端接口**：在 `DocumentController#getUserUploadedFiles` 的每条文件 DTO 中增加 `parseStatus`，值直接来自 `FileUpload.getParseStatus()`；不改变原有 `status` 的含义和接口路径。
2. **前端类型**：在 `frontend/src/typings/api.d.ts` 的 `Api.KnowledgeBase.UploadTask` 增加可空的 `parseStatus` 字段。可以定义单独的解析状态类型，避免与 `UploadStatus` 混用。
3. **上传完成时**：`mergeFile()` 成功后仍保留上传完成状态，但把页面所需的处理状态初始化为待处理。不要把这个时刻展示成“处理完成”。
4. **列表同步与渲染**：`index.vue#getList` 刷新已有行时也同步 `parseStatus`，且保留本地上传中的 `File`、分片进度等字段；状态列根据上传状态和解析状态共同渲染，文字要能独立表达含义，不能只靠颜色。
5. **自动刷新**：页面加载后，如果列表中存在已合并且 `parseStatus` 为 `null/0/1/3` 的文件，约每 3–5 秒刷新一次文件列表；本地文件刚合并成功后也应进入该刷新流程。一次只允许一个轮询器和一个进行中的请求。所有待处理文件都到 `2/4` 后停止，组件卸载时清理定时器。手动刷新继续可用。

## 验收用例

1. 合并成功后，页面先显示“上传完成，等待处理”，不得直接显示“处理完成”；后台转为 `1`、`2` 时，页面无需手动刷新即可依次显示“处理中”“处理完成”。
2. 处理一次失败且 Kafka 还在重试时，`parseStatus=3` 显示“处理中（重试中）”；随后若重试成功显示“处理完成”，若进入死信队列、状态为 `4` 则显示“处理失败”。
3. 对于 `null/0/1/2/3/4` 各状态，刷新浏览器页面后显示结果与表格一致；重新进入页面也一样。
4. 未合并文件继续显示现有上传进度或上传中断，不因缺少 `parseStatus` 被当作处理失败。手动刷新、续传、删除保持可用。
5. 列表接口暂时失败时，不得把文件误显示为“处理完成”或“处理失败”；页面恢复后仍可继续获取状态。
6. 自动刷新不会产生重叠请求或多个定时器；没有待处理文件时停止，离开页面后不再发请求。

## 验证与交付

- 至少检查上述状态映射、一次正常处理路径、一次最终失败路径，以及页面刷新后的状态恢复。没有方便的真实失败环境时，可通过接口模拟数据验证前端映射，并说明哪些路径没有端到端验证。
- 在 `frontend/` 执行 `pnpm typecheck`；如修改 Java 代码，执行项目可运行的相关构建或测试。报告实际命令和结果，不要把未运行的测试写成通过。
- 完成后列出改动文件、关键行为和仍存在的限制。此任务不要求调整 Kafka 重试、文件合并、向量化或检索逻辑。

## 已知边界

- `parseStatus=3` 是一次处理尝试的异常，后台可能正在重试；`4` 才是当前实现中的最终失败信号。
- 本次仅让页面反映后端已持久化的状态。若 Kafka 消息未成功发出、状态写库失败或死信状态写库失败，单靠前端无法保证状态最终收敛；请不要把这些情况表述为本次已修复。
