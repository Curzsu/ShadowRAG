# ShadowRAG 文档维护方案（精简版）

> 状态：2026-10-09 已完成文档整理、本地 CI 检查实现及最终独立审查；远端 GitHub Actions 尚未运行。
> 本轮实施分支：`codex/documentation-maintenance`。以下复选框记录实际实施进度。

**目标：** 读者能找到当前有效说明，开发时能顺手更新，旧资料不再被误认为当前能力。

**做法：** README 提供入口，文档索引区分当前指南与历史资料；先整理聊天、部署、可观测三份指南，再接入轻量链接检查。文档描述所在分支的实际代码，随功能一起合并。

## 1. 审查结论：哪些需要简化

| 原方案中偏重的要求 | 调整后 |
| --- | --- |
| 全库每份 Markdown 都分类、指定主题，完成后才能验收 | 全库浏览入口和路径依赖，只登记会误导使用的问题；其余按需处理 |
| 提前安排架构、检索、入库、记忆、权限等多份新指南 | 首轮只做三份指南；后续出现重复说明或真实阅读需求再拆主题 |
| 所有指南都维护性质、日期、状态及多种状态词 | 当前指南注明与本分支同步；旧资料按需加一句历史说明，不强制逐篇维护日期和状态表 |
| 维护约定复制完整职责表、影响映射和流程 | `AGENTS.md` 只放简短可执行规则；按改动查找相关文档 |
| 提前指定自研 Markdown 解析器、测试文件和基线格式 | 先验证现成工具能否满足本地链接检查；仅在有实际缺口时增加薄脚本 |
| 首次完成依赖一次未来真实功能变更和首次发布 | 首轮按本轮产物验收，后续交付和发布时应用规则 |

保留此前确认的统一入口、文档随代码更新、交付检查、渐进式 CI 和 CHANGELOG。简化工作量，不降低内容真实性要求。

## 3. 首轮目录与内容分工

| 文件 | 放什么 |
| --- | --- |
| `README.md` | 项目介绍、最短启动步骤、统一文档入口 |
| `docs/index.md` | 当前指南的阅读顺序；另列设计计划、研究评测、面试等资料入口 |
| `docs/chat.md` | 当前聊天与 SSE 行为、取消、超时、保存边界和常见排障 |
| `docs/deployment.md` | 依赖、配置、端口、启动、CPU/GPU、前端发布和 Nginx 使用条件 |
| `docs/observability.md` | 已有 Langfuse 能力、启用方法、评测入口、采集与验证局限 |
| `docs/ci.md` | 沿用现有文件，补检查方式和文档检查说明 |
| `AGENTS.md` | 给实施者和 AI 的简短文档维护规则 |
| `CHANGELOG.md` | 使用者可感知的功能、配置或迁移变化 |

不预建空白主题文件，不为每份历史材料制作一份索引条目。目录入口加少量重要资料链接即可；后续主题完成正文核对后再加入导航。

同一项详细说明保留一个维护位置，其他地方链接过去。README 在详细指南可用后再删重复内容，保证启动步骤始终可读。

## 4. 日常只维护这些规则

将以下规则简写到 `AGENTS.md`，不另建审批、责任登记或文档管理系统：

1. 文档与所在分支代码一致，接口、配置、操作流程变化时，在同一改动中更新相关说明。
2. 每次交付用一句话说明文档影响：更新了哪些文件；没有影响时说明具体原因。
3. 命令和默认值核对源码、脚本及公开配置；可选功能不等于已经启用，计划不等于已实现。
4. 实现与验证分别说明。例如“脚本已实现、少量样本联调通过”不能写成“正式评测已验收”；未执行的检查不能写成通过。
5. 新建当前指南在开头注明“与本分支代码同步”，链接少量关键实现入口；不要求逐次更新日期或提交号。
6. 旧资料容易误导时，在顶部说明记录时间或历史范围，并链接当前指南。保留原始结果与结论，不猜测缺失的历史环境。
7. 使用仓库相对链接；不移动脚本依赖的文件，不把私有配置加入公开导航。

CHANGELOG 从 `Unreleased` 开始，只记录真实、使用者可感知的变化；按需使用 Added、Changed、Fixed 等分类，不建空分类。正式发布时再按真实发布范围整理版本号和日期，不补造历史版本。已发布记录有误时注明勘误。

## 5. 实施步骤

### 第一步：建立入口，整理当前说明

**修改范围：** README、索引、根维护约定、CHANGELOG、三份当前指南，以及必要的历史提示。

- [x] 浏览 Git 跟踪的文档和主要入口，确认脚本路径依赖；只登记明显冲突、失效命令和影响阅读的问题。
- [x] 建立 `docs/index.md`，当前指南与历史资料分组；不存在的文件不做链接。
- [x] 建立简短 `AGENTS.md` 与 `CHANGELOG.md` 的 `Unreleased`。
- [x] 核对聊天相关后端和前端实现，整理 `docs/chat.md`。
- [x] 核对公开配置、Compose、启动脚本、前端配置及 Nginx 配置，整理 `docs/deployment.md`。
- [x] 核对追踪配置与 `scripts/langfuse/`，整理 `docs/observability.md`，区分实现、联调与正式评测。
- [x] 修正 README 路由命令，核对 Token／费用追踪、隔离方式、测试范围等表述；证据不足时收窄描述。
- [x] README 接入索引，详细指南可用后删除重复细节；为最容易混淆的旧评估、面试说明和阶段记录加历史提示。

**验收：** 从 README 能找到当前聊天、部署、可观测和测试说明；旧资料不会充当默认使用指南；新入口没有坏链接；原有脚本路径保留。

这一步即可独立交付，不等待所有历史文档清理完毕。

### 第二步：接入轻量文档 CI

**修改范围：** `.github/workflows/ci.yml`、`docs/ci.md`，以及实际需要的工具配置；必要时增加 `scripts/docs/` 中的薄脚本和历史问题清单。

- [x] 先以报告方式扫描本地链接，确认真实问题数量与工具误报；优先验证现成工具，固定所选工具版本。
- [x] 少量历史错误直接修复；不能立即修复的旧问题逐条登记豁免，记录来源与目标，不以整个历史目录作为永久豁免。
- [x] 接入独立 CI 检查任务，阻断新增本地坏链接、缺失入口和新增本机绝对路径链接。
- [x] 验证新增坏链接、删除被引用目标、历史豁免、中文／空格路径、引用式链接和代码块示例的处理是否符合预期。
- [x] 在 `docs/ci.md` 写清本地运行方式、失败修复方法和历史问题清理方式。

**检查边界：**

- 扫描根 README、AGENTS、CHANGELOG 及 Git 跟踪的 `docs/**/*.md`；扫描全部受管文档，确保删除目标也能发现未修改来源中的坏链接。
- 新入口和三份当前指南不使用历史问题豁免；历史豁免只匹配已确认的问题，修复后移除，不能自动吸收新增错误。确需新增豁免时说明原因并由维护者审查。
- 必要入口为 README、索引、AGENTS、CHANGELOG 和首批指南；确认 README → 索引 → 当前指南连通。其余只检查文件目标存在，首版不做标题锚点、外部网站可达性、文档更新时间或内容语义校验。
- 跳过代码示例中的链接文本；正文和代码块里的环境路径可以保留。本地链接支持中文、空格及 URL 编码。
- 不依赖数据库、GPU、模型 API 或前端构建；工具安装可以联网，检查本身不访问外部链接。
- 若现成工具无法实现上述边界，先确认具体缺口，再增加最小适配代码；不自研通用 Markdown 解析器。自写逻辑需覆盖相应行为用例，不为第三方工具重写整套测试。

**验收：** 新增坏链接和删除目标能阻断；已有问题可逐步清理；文档任务独立运行，内容是否准确仍结合代码审查。

### 后续：按实际改动维护

- 功能改动触及未覆盖主题时，先更新现有相关说明；内容确实需要独立维护时再建立新指南。
- 顺手清理碰到的旧链接和过期提示，不要求一次重写全部研究、计划和评测记录。
- 下次真实功能交付时应用文档影响说明，下次真实发布时整理 CHANGELOG；两者不作为本轮整理的等待条件。

## 6. 验证与完成标准

首轮整理完成以第一步验收为准；第二步接入 CI 后，再验收自动检查。不能将仅完成方案或整理文档表述为 CI 已上线。

纯文档改动只核对内容依据、相对链接和变更差异，不因此运行整套业务测试或付费模型评测。新增检查脚本时验证其实际行为；若修改了运行脚本或依赖路径，再进行对应验证。
