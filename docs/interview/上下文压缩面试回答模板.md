# ShadowRAG 上下文压缩：面试回答模板

> 适用场景：大厂日常实习、Java 后端、AI 应用/RAG 项目面试。  
> 使用方法：先背熟 30 秒版和 1 分钟版，再按面试官追问选择后面的模块。不要一上来把所有细节全倒出来。

## 一句话定位

这套设计不是“把历史随便截短”，而是把**完整性、性能和模型上下文安全**拆成三层：MySQL 保存不可被压缩覆盖的原始消息，Redis 保存可重建的压缩工作集，真正调用模型前再做一次 token 预算兜底。

## 30 秒回答

> 我把会话历史分成了事实层和工作集层。每轮完成后，先在 MySQL 的 `conversation_messages` 里事务追加原始 user/assistant 消息，再用 Redis Lua 原子追加到工作集并递增版本号。工作集超过 2 万 token 时异步做增量摘要，超过 5 万时同步截断，但这些操作都不会修改 MySQL 原文。异步摘要写回时带读取前的 version，通过 Lua 做 CAS，避免压缩期间有新消息时发生丢失更新。最后，在 Agentic RAG 的第一次和第二次模型调用前都会重新计算完整请求预算，算上 tools、输出预留和安全余量；必要时按整轮删除旧历史，或者只截断过大的 tool result。所以后台压缩负责成本和延迟，调用前预算负责正确性，两者职责是分开的。

## 1 分钟回答

> 最初版本只有 Redis JSON 和异步摘要，基本流程能跑，但我认为有三个工程风险。第一，压缩结果再同步到 MySQL 会让摘要覆盖原文，恢复不了完整历史；第二，LLM 摘要期间如果新消息到达，旧快照可能覆盖新消息；第三，只在消息结束后检查阈值，不能保证下一次真实请求一定不超过模型窗口，尤其 Agentic RAG 第二次调用还会突然加入很大的检索结果。
>
> 我的改法是三层防线。第一层是数据完整性：MySQL 改成 append-only 原始消息表，每条消息有数据库序号，Redis 只是可丢弃工作集；普通读取遇到 cache miss 或损坏数据会自动从 MySQL 回源重建，切换会话也复用该流程。第二层是并发正确性：消息追加、版本递增和 TTL 更新放在同一个 Lua 中；异步摘要先读 version 和快照，LLM 完成后用 version CAS 原子替换，冲突就丢弃旧摘要；会话重建同样走 CAS，追加再按数据库 seq 去重和排序。JVM 内的任务表只用于减少重复调用，不承担正确性。第三层是请求安全：聊天两次调用和后台摘要调用都在发送模型前执行预算；聊天请求保留 system、当前 user 和工具协议尾部，优先淘汰最老的完整对话轮次，检索结果过大时二分截断 tool content。这样即使异步压缩失败或来不及完成，请求仍然不会依赖它来守住上下文窗口。

## 3 分钟完整回答

> 这个功能的目标有四个：原始对话可恢复、在线请求不能超窗口、压缩不阻塞主链路、并发下不能丢新消息。
>
> 写路径上，首次请求在调用模型前就通过 `ConversationService.createConversation` 建好 MySQL 父记录，而不是只在 Redis 里生成 UUID。模型完整回答后，`ConversationMessageService.appendTurn` 在一个 MySQL 事务里追加 user 和 assistant 两条原始消息，并通过会话行悲观锁把同一会话的并发轮次串行化；数据库生成的 id 同时作为消息 seq。只有数据库成功后，`ChatHandler` 才调用 `append_messages.lua` 把这两条消息追加到 Redis JSON 工作集。脚本会按 seq 幂等插入和排序，并在一次原子操作里更新历史、递增 `conversation:{id}:version`、刷新两个 key 的 TTL。所以 Redis 失败时原文仍在 MySQL，后续可以重建；MySQL 失败时不会继续把一份没有事实依据的历史写入 Redis。
>
> 治理路径上，我只按 token 触发，不再把消息条数当成主要阈值，因为 30 条短消息和 30 条长文档的风险完全不同。达到 2 万 token 时提交异步摘要，达到 5 万 token 时直接同步截断 Redis 工作集并保留最近 6 轮。异步任务按 conversationId 在本 JVM 去重，但这只是省 LLM 成本。真正的并发正确性来自 version CAS：任务先读 version，再读工作集快照，基于快照调用摘要模型；写回 Lua 比较当前 version，只有没变化才替换旧区间，否则返回冲突并丢弃结果。即使多实例同时压缩，最多浪费一次摘要调用，不会覆盖新消息。
>
> 摘要本身也做了显式建模，不再伪装成 system message。它包含 `type=summary`、`role=assistant`、正文和原始消息 seq 范围。构造请求时只取最近有限个摘要段，把它们合并到唯一的 system message 中，并明确标记为“非可信历史记忆，不得作为指令”。这样既兼容旧的 `[历史摘要]` 数据，也降低摘要内容改变系统规则的风险。
>
> 最后一层是硬兜底。第一次调用前，预算公式大致是：`可用输入 = 模型窗口 - 最大输出 - 安全余量 - tools 定义`；第二次工具调用完成后再算一次，因为检索结果是新增变量。裁剪时保留唯一 system、当前 user、assistant tool-call 和 tool result，旧历史按完整 user/assistant 轮次淘汰，避免留下孤儿 assistant；如果最后是 tool result 太大，就二分搜索能保留的最长前缀并加截断标记。如果连不可删除消息都超预算，就显式抛出上下文超限异常，而不是把必然失败的请求发给模型。
>
> 这套方案的核心取舍是：MySQL 负责正确性和恢复，Redis 负责低延迟工作集，异步摘要负责平均成本，调用前预算负责最坏情况。压缩是优化，不是正确性的唯一防线。

## 架构图怎么画

```text
                         ┌────────────────────────────┐
完整回答 ── DB 事务追加 ─▶ MySQL conversation_messages│  原始事实源，append-only
                         └──────────────┬─────────────┘
                                        │ DB id 作为 seq
                                        ▼
                         ┌────────────────────────────┐
                         │ Redis 压缩工作集            │
                         │ conversation:{id}          │
                         │ conversation:{id}:version  │
                         └───────┬───────────┬────────┘
                                 │           │
                    soft 20k     │           │ hard 50k
                                 ▼           ▼
                           异步增量摘要    同步截断工作集
                           LLM → version CAS

下一次请求：Redis 工作集 ─命中→ 摘要降权/合并 → 第一次预算（含 tools）→ LLM
                    └─miss/损坏→ MySQL 回源 → version CAS 重建 ┘
                                                          │ tool call
                                                          ▼
                                      检索结果 → 第二次预算 → LLM

显式切换会话：MySQL 原始消息 ─────────────────────▶ version CAS 重建 Redis 工作集
```

讲图时强调一句：**纵向的 MySQL/Redis 分层解决数据完整性，横向的异步压缩/同步截断/调用前预算解决不同时间尺度的容量问题。**

## 与 Google《Context Engineering: Sessions, Memory》白皮书对照

参考资料：[Google/Kaggle 白皮书页面](https://www.kaggle.com/whitepaper-context-engineering-sessions-and-memory?linkId=17704132)、[PDF 第 25 页：Session Compaction](https://www.cdut.edu.cn/__local/2/CC/D2/C44B0CC9F8978C5BFA029413538_450FAE19_730DBA.pdf#page=25)、[PDF 第 56 页：Background vs. Blocking Operations](https://www.cdut.edu.cn/__local/2/CC/D2/C44B0CC9F8978C5BFA029413538_450FAE19_730DBA.pdf#page=56)、[PDF 第 67—68 页：Production Considerations](https://www.cdut.edu.cn/__local/2/CC/D2/C44B0CC9F8978C5BFA029413538_450FAE19_730DBA.pdf#page=67)。

客观结论：**当前实现满足白皮书“昂贵的 LLM 压缩不能阻塞用户”的核心原则，但只实现了单体应用内的异步 Session Compaction，不是完整的生产级 Memory Service。**

| 白皮书关注点 | 当前实现 | 判断 |
|---|---|---|
| 昂贵的递归摘要在后台执行 | 用户响应完成后，由 `compressionExecutor` 执行摘要 LLM 调用 | 满足 |
| 用阈值决定何时压缩 | 2 万 token 触发异步摘要，属于白皮书认可的 Token/Count-Based Trigger | 满足 |
| 调用模型前按 Token 控制上下文 | 两次聊天 LLM 调用前都执行预算；工具结果过大时单独截断 | 满足 |
| 保存摘要覆盖的原始事件范围 | 摘要记录 `sourceStartSeq/sourceEndSeq` | 满足 |
| 并发生成不能覆盖新事件 | Redis version CAS；版本冲突时丢弃过期摘要 | 满足 |
| 持久化压缩结果以避免重复计算 | 摘要保存在带 TTL 的 Redis；MySQL 只保存不可变原文 | 部分满足：Redis 丢失或过期后可能重新摘要 |
| 压缩/记忆生成与 Agent Runtime 架构隔离 | 使用同 JVM 的独立线程池 | 部分满足：异步但未拆成独立服务 |
| 可靠任务队列、进程重启恢复、DLQ | 有界内存队列、有限重试和拒绝日志 | 未完全满足：重启会丢在途任务，没有持久队列和 DLQ |
| 跨 Session 的长期用户记忆 | 当前只维护单会话摘要工作集 | 不属于当前功能范围，不能称为完整 Memory Manager |

### 为什么同步硬截断不违反白皮书？

> 白皮书要求异步化的是递归摘要、记忆提取这类需要额外 LLM 调用和数据库处理的昂贵操作。本项目在 5 万 token 硬阈值执行的只是确定性的 Redis Lua 截断，不调用摘要模型；两次调用前的 Token 预算也是构造安全请求必需的 hot path。因此，异步摘要负责降低平均成本和延迟，同步截断与调用前预算负责最坏情况下的正确性，两者并不冲突。

### 可以直接背诵的白皮书对照回答

> 我的实现遵循了 Google Context Engineering 白皮书的核心原则：昂贵的 LLM 摘要不会放在用户请求链路同步执行，而是在回答发送完成后提交到独立线程池；同步路径只保留 Token 预算和 Redis Lua 截断作为安全兜底。摘要会记录原始消息 seq 范围，并通过 version CAS 防止异步旧快照覆盖新消息。当前是单体应用内的异步化实现，不是完整的独立 Memory Service；如果生产规模继续扩大，我会把任务迁移到可靠队列和独立 Worker，把摘要存入单独的持久化表，并增加指数退避和 DLQ。

## 面试官高频追问

### 1. 为什么不能只把历史存在 Redis？

> Redis 在这里更适合做低延迟工作集，而不是唯一事实源。它会过期，也可能因为故障、误删或内存策略丢数据；更关键的是，工作集会被摘要和截断。如果直接把压缩后的 JSON 回写数据库，原文就不可逆丢失。现在 MySQL 只追加原始消息，Redis 可以随时从 MySQL 重建，压缩失败也不会影响审计和恢复。

### 2. 为什么单独建消息表，不继续用 `conversations.messages` 的大 JSON？

> 大 JSON 每轮都需要读、反序列化、整体拼接和整行覆盖，写放大明显，并发更新也容易丢失。拆成消息表以后，每轮是两条 append，同一会话先锁定会话行，数据库 id 提供稳定顺序，查询按 `(conversation_id, id)` 索引扫描。旧 JSON 字段保留只读兼容，避免一次性迁移阻塞上线。

补充取舍：当前使用全局自增 id 作为 seq，足够保证单会话内顺序；如果未来需要分库分表，会改成会话内序号或雪花 id，并增加唯一约束。

### 3. 为什么先写 MySQL，再写 Redis？

> 因为原始事实的优先级更高。MySQL 失败就终止历史更新，避免 Redis 出现数据库里不存在的“幽灵消息”；MySQL 成功但 Redis 失败，原文仍然安全。若 Redis key 缺失，下一次普通聊天读取会自动回源重建；若旧 key 仍存在，当前可能短暂读到旧视图，要靠 TTL 或显式恢复，后续可加 outbox 主动修复。这是一个明确的 fail-closed 顺序，但不是强一致分布式事务。

### 4. 这是不是分布式事务？如何保证 MySQL 和 Redis 一致？

> 不是强一致分布式事务，也没有假装成 2PC。当前保证的是 MySQL 事实优先和可恢复：DB 先提交，Redis 后更新。DB 成功、Redis 失败时会短暂不一致，但不会丢原文。更高要求下我会加 outbox：MySQL 同一事务记录待同步事件，由后台幂等消费刷新 Redis，再用消息 seq 去重。

### 5. 为什么压缩按 token，不按消息条数？

> 模型限制的资源是 token，不是消息条数。一条粘贴的长文可能比几十条短问答更大；条数阈值既可能过早压缩，也可能漏掉突发大消息。所以治理阈值统一用 token。消息封装、tools 和输出空间则在真正调用前统一预算。

### 6. soft threshold 和 hard threshold 有什么区别？

> 软阈值 2 万 token 是性能优化信号，异步调用摘要模型，避免阻塞用户；硬阈值 5 万 token 是 Redis 工作集的容量保护，直接同步保留最近 6 轮。它们都不是最终的模型窗口保护，真正的硬兜底是每次调用前的预算。

### 7. 已经有硬阈值，为什么还要调用前预算？

> 硬阈值是在上一轮结束后检查，存在时间差；而一次真实请求还会加入当前问题、system prompt、tools 定义、输出预留。Agentic RAG 的第二次调用还会新增 tool-call 和检索结果。因此只有在每次发送请求前计算最终 payload，才能对“这一次调用”负责。

### 8. token 是怎么估算的？准确吗？

> 当前统一用 `cl100k_base` 做本地近似估算，并把消息 JSON 和固定封装开销算进去。部署模型是 GLM，因此我不会宣称估算与服务端完全一致；代码另外预留 2048 token 安全边界。生产上更理想的做法是接入供应商 tokenizer，或者根据服务端 usage 反校准安全系数。

### 9. 第一次模型调用具体预算了什么？

> `模型窗口 - max output - safety margin - tools schema` 得到消息可用预算。固定 system 和当前 user 不删，旧历史从最老的完整 user/assistant 轮次开始淘汰。如果不可删除部分本身超限，则提前报错。

### 10. 第二次调用为什么要单独预算？

> 因为检索结果在第一次调用时还不存在，而且大小波动最大。第二次会保护当前 user、assistant tool-call、tool result 这三个协议消息；先淘汰更老历史，再对 tool content 做二分截断。这样既满足 Function Calling 消息协议，也最大化保留检索内容。

### 11. 为什么按完整轮次删除？

> 如果逐条删除，可能删掉 user 却留下对应 assistant，模型会看到语义断裂的历史。预算器会识别最老的 user/assistant 对并一起删除；工具调用尾部则作为一个受保护协议单元。

### 12. 如果当前用户消息本身就特别大呢？

> 当前 user 是不可删除消息。如果 system 加当前 user 已经超过可用预算，代码会抛 `ContextWindowExceededException`，不会偷偷截断用户意图或把必然失败的请求发出去。产品层可以再把这个异常映射为“请缩短输入或改为上传文档”。

### 13. 为什么摘要要异步？

> 摘要 LLM 的延迟和失败率都不应该进入用户回答主链路。异步可以降低 P99 延迟；与此同时，调用前预算保证即使摘要尚未完成、执行失败或队列已满，下一次请求仍然安全。所以异步化不会削弱正确性。

### 14. 异步压缩时有新消息进来，会不会被覆盖？

> 不会直接覆盖。任务先读 version，再读快照，完成 LLM 调用后把 expected version 传给 Lua。Lua 在 Redis 内比较当前 version，相同才替换；消息追加也在 Lua 内原子递增 version。只要期间发生过追加、截断或会话重建，CAS 就失败，旧摘要被丢弃。

### 15. 为什么先读 version，再读 history？

> 如果先读 history、后读 version，二者之间发生追加时，可能拿到旧快照和新版本，CAS 反而错误通过。先读 version 后读快照时，只要两次读取之间发生变更，最终写回看到的当前 version 就与 expected version 不同，必然冲突。

### 16. Lua 已经原子，为什么还要 version CAS？

> Lua 只能保证“执行脚本的那一瞬间”原子，不能让脚本外几十秒的 LLM 调用变成原子事务。version 把读取快照到写回之间的长时间窗口纳入乐观并发控制。Lua 负责原子比较和替换，version 负责判断摘要是否过期，两者缺一不可。

### 17. 为什么不用 Redis 分布式锁锁住整个摘要过程？

> LLM 调用可能几十秒，长时间持锁会阻塞消息写入，还要处理锁续期、进程崩溃和误释放。这里冲突概率可接受，更适合乐观并发：允许计算，写回时 CAS，冲突就丢弃。用户消息始终可以正常追加。

### 18. `ConcurrentHashMap` 能解决多实例并发吗？

> 不能，也不承担这个职责。它只在单 JVM 内减少同一会话的重复摘要调用，节省成本。多实例下可能有两个摘要任务同时跑，但 Redis version CAS 保证最多一个过期条件满足，不会丢消息。若摘要成本成为瓶颈，再加带租约的分布式任务去重。

### 19. 本地任务去重有没有生命周期问题？

> 我没有直接用 `computeIfAbsent + runAsync`，因为任务如果在映射真正插入前就同步完成，可能留下一个 completed future，后续永远无法再提交。现在先用 `putIfAbsent` 放占位 future，再提交 executor，并在任务完成、异常或拒绝时用二元 `remove(key, marker)` 清理。这个边界有专门回归测试。

### 20. 线程池满了怎么办？

> 提交会捕获 `RejectedExecutionException`，清理会话去重槽并记录日志，不阻塞聊天主链路。工作集可能暂时不压缩，但调用前预算仍然守住模型窗口，下一轮检查还能重新提交。

### 21. 摘要模型失败或超时怎么办？

> 有超时和有限重试；最终失败就保留当前 Redis 工作集，不影响 MySQL 原文。后续新消息再次达到阈值时可以重新触发。即使一直失败，硬截断和调用前预算仍然可用。

### 22. 为什么做增量摘要，不每次重写全部历史？

> 增量只处理最新摘要边界之后、最近保留轮次之前的新消息，LLM 输入和成本更稳定，也减少反复总结造成的事实漂移。旧摘要可以作为理解上下文，但提示模型只总结新增区间。

### 23. 多段摘要不会一直增长吗？

> Redis 中可能保留多个增量摘要段，但请求构造只取最近 `max-summary-segments` 个，当前默认 3，避免 system prompt 无界增长。更长期的方案可以在后台做低频分层合并，并配合事实一致性评测，而不是在在线请求里同步再摘要。

### 24. 为什么摘要不是 `role=system`？

> 摘要是模型生成、可能失真，也可能包含用户输入中的指令文本，不具备系统规则的信任级别。存储时显式标为 `type=summary, role=assistant`；构造请求时统一放进一个带“非可信记忆”边界的 system 内容块，并过滤工作集里其他 system role，避免形成多个相互竞争的系统消息。

注意：这只是提示词层防御，不应夸成绝对防注入。更高安全要求下还应做摘要内容过滤、结构化事实抽取和对抗评测。

### 25. `sourceStartSeq/sourceEndSeq` 有什么用？

> 它让摘要具有可追踪来源：可以知道这个摘要覆盖了哪些原始消息，便于排查事实丢失、做离线质量评估，或从 MySQL 重新生成。当前旧数据没有 seq 时会用位置标记兼容，新数据使用数据库 id。

### 26. Redis key 为什么都设 TTL？

> 历史工作集和 version 的生命周期必须一致，否则历史过期但旧 version 残留会增加恢复和排障复杂度。追加、压缩、截断都会保持或刷新二者 TTL；删除会话时也同时删除两个 key。

### 27. 会话切换怎么恢复？

> `ConversationService.switchConversation` 先读工作集 version，再读取 `conversation_messages`，并把升级前的 `conversations.messages` 只读快照放在新消息之前。完整结果通过 Lua CAS 原子重建；若期间发生追加或压缩，CAS 冲突后会重新读数据库，最多重试三次。这样既保留旧会话快照，也不会用普通 SET 覆盖正在追加的新消息。

### 28. 压缩后还能查看完整聊天记录吗？

> 能。压缩和硬截断只改变 Redis 工作集，MySQL 原始消息不被覆盖。展示完整记录或重建工作集时读消息表。旧版本那种把压缩 JSON 回写数据库的方法已经移除。

### 29. 时间复杂度和性能瓶颈是什么？

> MySQL 追加是 O(1) 级别的顺序写；按会话读历史是索引顺序扫描。当前 Redis 工作集用 JSON 数组，Lua 追加、截断和替换需要解码/编码整个数组，是 O(n)，但工作集受 token 阈值控制，不会无限增长。规模继续增大时，我会把 Redis 结构改为 Stream/List，摘要元数据单独存储，避免整体 JSON 重写。

### 30. 为什么不用 Kafka 做会话写入？

> 当前原始对话完整性要求在本轮结束时就明确落库，直接事务追加路径更简单。Kafka 更适合后续 outbox 同步 Redis、离线摘要或分析，不适合为了“异步”而让事实落库状态变得难以判断。

### 31. 为什么不用向量数据库做长期记忆？

> 向量记忆解决的是“从大量历史里按语义召回”，摘要工作集解决的是“维持连续对话状态和近期决策”。两者互补。当前项目的会话规模先用摘要加近期窗口就够；如果跨月历史很大，可以把原始消息或结构化事实异步向量化，再把召回结果也纳入同一个调用前预算。

### 32. 怎么测试这套设计？

> 单元测试覆盖六组关键不变量：MySQL 两条原始消息事务追加；Redis 命中时不查库，miss 或损坏时自动从 MySQL 恢复；会话恢复合并旧快照和新消息，并在重建 CAS 冲突后重读；Redis append/rebuild 的 key、TTL、seq 和 version 脚本调用契约；摘要 version 冲突时丢弃、结构化摘要带来源范围、摘要 prompt 超限时不调用模型；聊天两次调用前预算、完整轮次淘汰、tool result 截断和不可裁剪时拒绝。另外还覆盖了任务去重槽在同步完成后能释放。生产前仍需要用真实 Redis 跑 Lua 并发集成测试，并用实际模型 tokenizer 做边界回归。

### 33. 你会关注哪些指标？

> 当前代码已经记录阈值判断、压缩结果、冲突、重试和任务拒绝日志。下一步我会加 Micrometer 指标：工作集 token 分布、压缩耗时和成功率、CAS 冲突率、队列深度、硬截断次数、预算裁剪 token 数、上下文拒绝次数，以及 MySQL 成功但 Redis 更新失败的修复积压。不要说这些指标已经实现，目前只是演进方案。

### 34. 现在到底是 Cache-Aside 还是 Read-Through？

> 严格按模式归类，它仍是应用管理的 Cache-Aside：业务代码先查 Redis，miss 后显式查 MySQL，再回填 Redis，并不是缓存中间件自己透明加载数据库。不过我把这段逻辑封装成统一恢复入口，所以从调用效果看具备 application-level Read-Through 语义。写路径仍然是 MySQL 事实层先提交、再更新 Redis 派生视图，不是 Write-Through。这样回答既说明了自动回源，也不会把模式名称说错。

## 故障矩阵速答

| 故障点 | 当前行为 | 数据是否丢失 | 后续策略 |
|---|---|---:|---|
| MySQL append 失败 | 不继续更新 Redis，记录错误 | 本轮历史未入库 | 告警/重试；未来加请求幂等键 |
| MySQL 成功、Redis append 失败 | 原文已在事实层；旧 key 仍在时可能短暂读旧视图 | 否 | key miss 自动回源；TTL/显式恢复兜底；未来可用 outbox 主动修复 |
| Redis 工作集 miss/JSON 损坏 | 自动从 MySQL 读取并用 version CAS 重建 | 否 | 记录 miss、回源延迟和重建结果 |
| 摘要 LLM 失败/超时 | 重试后放弃本次压缩 | 否 | 下轮重试，预算器兜底 |
| 摘要期间有新消息 | Lua CAS 返回冲突，丢弃旧摘要 | 否 | 下轮重新压缩 |
| 线程池满 | 清理去重槽，不阻塞聊天 | 否 | 下轮重试，监控队列 |
| Redis 工作集超过硬阈值 | 同步保留最近 6 轮 | MySQL 原文不丢 | 下次请求仍做预算 |
| tool result 过大 | 二分截断 tool content | 检索上下文部分减少 | 添加明确截断标记 |
| 必需消息本身超窗口 | 请求前显式拒绝 | 否 | 提示缩短输入/改为文档 |

## STAR 行为面试模板

### Situation

> 项目需要支持长对话和 Agentic RAG。旧实现把整段历史作为 Redis JSON，达到阈值后异步摘要并回写 MySQL。

### Task

> 我的目标是让压缩不阻塞主链路，同时保证原始历史可恢复、并发消息不丢、两阶段模型调用都不会超窗口。

### Action

> 我先把数据职责拆开：MySQL append-only 原文、Redis 压缩工作集。然后用 Lua 把消息追加、版本递增、TTL 更新原子化，用 version CAS 保护跨 LLM 调用的长事务。最后新增统一 token 估算和调用前预算，分别接入两次模型调用，并对摘要做结构化和信任降级。我用失败测试先复现孤儿 assistant、过期摘要覆盖以及异步去重槽不释放，再改实现跑绿。

### Result

> 现在压缩结果不会覆盖数据库原文；并发追加会使旧摘要 CAS 失败；异步压缩失败时仍有同步工作集治理和请求前预算；检索结果过大时可以保留工具协议并有界截断。这里我会用测试覆盖和不变量来描述结果，不虚构线上 QPS 或延迟收益。

## 面试时不要夸大的点

- 不要说“token 计算百分之百准确”。当前 `cl100k_base` 对 GLM 是近似值，靠 safety margin 降低误差风险。
- 不要说“Lua 解决了所有并发”。Lua 解决单次 Redis 操作原子性，跨 LLM 调用靠 version CAS；本地任务表只省成本。
- 不要说“系统实现了 MySQL/Redis 强一致”。当前是 DB-first、可恢复的最终一致，严格修复需 outbox。
- 不要说“摘要绝对防 prompt injection”。目前做了角色降权、单 system 和非可信边界，仍需要对抗评测。
- 不要说“所有测试都通过”。项目全量测试还依赖本地 MySQL/Redis/ES 等环境；应区分本功能定向测试和环境型集成测试。
- 不要说“已经有完整监控大盘”。当前有日志，Micrometer 指标是下一步。
- 不要说“支持 exactly-once 写入”。当前事务保证一轮内两条消息同时成功；若未来引入自动重试，还需 requestId/turnId 唯一约束实现幂等。
- 不要说“完全实现了 Google 白皮书的 Memory Service”。当前实现的是 Session Compaction，线程池仍在 Agent 主服务进程内，也没有跨 Session 的长期用户记忆。
- 不要说“摘要已经耐久化”。摘要当前只在带 TTL 的 Redis 工作集；MySQL 耐久保存的是原始消息，Redis 丢失后可能重新生成摘要。

## 主动承认的下一步改进

如果面试官问“还有什么不足”，按优先级回答：

1. 给每个客户端请求增加 `turn_id` 唯一键，避免网络重试造成重复消息。
2. 用 transactional outbox 自动修复 MySQL 成功、Redis 失败的短暂不一致。
3. 增加真实 Redis Lua 集成测试和并发压测，而不只验证服务层脚本调用契约。
4. 接入实际部署模型 tokenizer，并用服务端 usage 持续校准估算。
5. 用 Micrometer 建立压缩成功率、CAS 冲突率、预算裁剪和修复积压指标。
6. 工作集更大时从整段 JSON 迁移到 Redis Stream/List，降低 Lua O(n) 编解码成本。
7. 对摘要做事实保真评测、敏感信息处理和 prompt injection 对抗测试。
8. 生产规模扩大后，将压缩任务迁移到可靠队列和独立 Worker，增加指数退避、DLQ 和任务可观测性。
9. 新建独立摘要表，持久化摘要内容、原始 seq 范围、生成版本和模型信息；Redis 仍只承担低延迟工作集，避免覆盖 MySQL 原文。

结束句可以这样说：

> 我没有把异步摘要当成唯一防线，而是把数据恢复、并发写入和请求预算分别建立不变量。这样某个优化环节失败时，系统只是成本变高或上下文变短，不会演变成原文丢失或并发覆盖。
