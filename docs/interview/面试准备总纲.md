## 〇、面试官的提问逻辑（先理解对手）

面试官拿到你的简历，提问路径几乎一定是：

1. **开场**（3-5 分钟）："做个自我介绍" / "介绍一下你的项目" —— 考察表达和宏观理解
2. **简历逐条追问**（20-30 分钟）：看到"混合检索 Hit@5 89%"→ 问混合检索怎么做；看到"竞态数据覆盖"→ 问竞态是什么怎么解决。**他只会针对简历上出现的名词和数字问。**
3. **开放性深挖**（10 分钟）："如果检索不准怎么排查" / "数据量翻 10 倍怎么办" —— 考察真实理解深度
4. **基础八股 + 行为面**（10-15 分钟）

所以：**简历没写的，他大概率不会主动问（除非开放性追问）；简历写了的，他一定会问。** 准备策略就是"简历每个技术点都准备好 3 层深度的答案"。

## 一、简历风险点：诚实是最高 ROI（必看，30 分钟）

你的简历总体扎实，但有几处表述"超出代码实际"，面试官深挖会翻车。**主动澄清 + 给出优化方向，比硬撑加分。**

### ⚠️ 风险 1：评测数字"Hit@5 89%、MRR 0.82、提升 17%"

**真相**：项目里只有一份评测**方案设计文档**（`docs/retrieval-evaluation-tutorial.md`），评测脚本和标注数据集**没正式跑通**，数字是设计阶段的预期目标值。

**应对（二选一）**：
- **保守**：被追问"这些数字怎么来的"时坦诚——"这是基于评测方案设计的预期目标值，标注数据集和脚本因时间原因还没正式跑完，目前只有小样本验证。"
- **突击（强烈推荐，ROI 极高）**：面试前花 2-3 小时，照着方案文档写出评测脚本，哪怕只跑 10 组小样本，把数字换成真实值。**把风险点变成"我做完了"。**

### ⚠️ 风险 2："TTFT 降低约 3s"

**真相**：代码里没有埋点和实测。"3s"是估算（naive RAG 对所有问题都做 embedding+ES，通用问答跳过这些步骤能省的开销）。

**关键反向**：知识库问答场景下，Agentic 比 naive **多一次 LLM 往返**（先判断要不要搜，再带结果生成），TTFT 反而**变高**。

**应对话术**：
> "这个 3s 是基于 naive RAG 对所有问题都做 embedding+ES 检索的开销估算，不是线上 A/B 实测。通用问答（'你好''1+1'）在 Agentic 下直接走单次 LLM 调用，省掉了 embedding+ES 这两步。但我要说明，知识库问答场景 TTFT 反而会增加，因为多了判断检索的 LLM 往返——这是 Agentic 的固有 trade-off。"

### ⚠️ 风险 3："Kafka 对上传、解析、切块、向量化全流程异步解耦"

**真相**：实际是**单 topic 单消费者同步串行**（一个 topic 里依次完成解析→分块→向量化），不是多 topic 流水线。简历"全流程异步解耦"略夸大。

**应对话术**：
> "目前是单 topic + 单消费者：上传后发一条消息，消费者里依次完成解析→分块→向量化→写 ES。我评估过拆成多 topic 流水线，但解析和向量化强耦合——解析失败必然要整体重试，拆开反而增加事务一致性复杂度，所以简化为单 topic。Kafka 在这里主要的价值是：上传请求快速返回（解析异步化）、重试+死信队列容错、流量削峰。如果吞吐成瓶颈，可以把向量化拆成独立 topic 并行。"

### ⚠️ 风险 4：MCP / Skill（技能栏写了，但项目里没实现）

**真相**：项目代码里**完全没有 MCP 协议实现，也没有 Skill 实现**。设计文档甚至明确写了"No MCP layer"。技能栏的"熟悉 MCP 协议"只能靠**通用知识 + 使用 Cursor 的 MCP 经验**撑。

**应对话术（千万别吹"项目实现了 MCP"）**：
> "项目里的 LLM 与知识库交互是通过 Function Calling（OpenAI 兼容的 tools API）实现的，这本质是 LLM 调用应用内的本地函数。MCP 我理解为把这种能力**标准化、协议化**——Server 可以是独立进程，任何 MCP Host（Claude Desktop、Cursor）都能接入。我自己平时用 Cursor 时接入了 firecrawl 等 MCP Server，对协议的 stdio / Streamable HTTP 两种传输和 Tools/Resources/Prompts 三种能力有了解。如果要给我的项目接入 MCP，我会把 search_knowledge_base 封装成一个独立的 MCP Server，让其他 Host 也能复用。"

> **注意**：被问"你项目里 MCP 怎么用的"，**直接说"项目里用的是 Function Calling，没用 MCP，但我理解两者的关系是……"**，不要绕。

## 三、六大技术模块深挖（核心，按简历出现顺序）

### 模块 A：混合检索 + RRF + Cross-Encoder（简历第一条亮点）

#### 你必须背熟的关键数字

| 配置项 | 值 |
|---|---|
| 向量维度 | 1024（bge-m3），cosine 相似度 |
| 召回窗口 | 每路召回 topK×30 条（当前 topK=10，即每路召回约 300 条，给 RRF 和 rerank 留候选） |
| RRF 常数 K | 60（业界标准经验值） |
| BM25 分词器 | IK 分词器（索引最细粒度，搜索智能切分） |
| Embedding 模型 | bge-m3（BAAI 出品，多语言，1024 维） |
| Reranker | bge-reranker-v2-m3（XLM-RoBERTa 架构的 Cross-Encoder，跑在 HuggingFace TEI） |
| chunk 大小 | 512 字符，按段落→句子→词三级递进切 |
| KNN num_candidates | ⚠️ 当前设成和 k 相等（= recallK），是已知可优化点（见 Q5 诚实补充） |

#### 面试官会问的问题

**Q1: 你的混合检索具体是怎么做的？讲讲完整流程。**
> 用户提问后，query 同时走两路：一路用 bge-m3 编码成向量，做 KNN 向量检索（cosine 相似度）；一路做 IK 分词后做 BM25 全文检索。两路各召回一批候选，然后在 Java 端用 RRF 算法融合排序，融合后的结果再过一遍 Cross-Encoder 精排，取最终的 top K 喂给 LLM 生成。
> 两路召回的原因：向量检索擅长语义匹配（query 和文档用不同词表达同一意思），BM25 擅长关键词精确匹配（专有名词、人名、术语）。两者互补，单用任一个都有盲区。

**Q2: RRF 融合是什么？为什么用它？**
> RRF（Reciprocal Rank Fusion，倒数排名融合）公式是 `score = Σ 1/(K + rank)`，K 取 60（业界经验值）。它的核心思想是**不看分数只看排名**——因为向量检索的 cosine 分数和 BM25 的相关性分数尺度完全不可比，直接加权没意义；RRF 用排名倒数，巧妙绕开了分数尺度问题。同一个 chunk 在两路都出现时，分数累加，重复命中的文档自然排到前面，这正是混合检索收益的来源。
> 实现上我用 `文件MD5:chunkId` 作为唯一 key 做去重和分数累加。

**Q3: 为什么需要 Cross-Encoder 精排？前面不是已经排过了吗？**
> RRF 融合后的排序只是"两路召回的共识排序"，不是真正的语义相关性排序。
> 向量检索（Bi-Encoder，双塔模型）的局限是：query 和文档**各自独立编码**，没有交互，精度有限。Cross-Encoder 把 query 和文档**拼一起喂给 Transformer**，每一层都有 attention 交互，能捕捉细粒度的语义关系，精度高得多。但 Cross-Encoder 计算成本是 O(n) 次 Transformer forward，只能对少量候选做精排。所以业界标配就是：双塔召回到大候选池 → Cross-Encoder 精排 top 几。这是经典的"召回求全、精排求准"两阶段架构。

**Q4: bge-m3 为什么选这个？对比 OpenAI embedding 怎么样？**
> 选 bge-m3 三点原因：① **多语言**，中英文都强（OpenAI 的中文不如国产）；② **开源可本地部署**，我用 Ollama 部署，数据不出企业，符合私有化知识库的需求；③ **效果是开源 SOTA**，BAAI 出品。
> 对比 OpenAI：OpenAI 是闭源 API，要花钱且数据要出企业，企业私有化场景不适合。
>
> **bge-m3 的"M3"含义（被问到要能答）**：三个 M 指它的三大特性——**M**ulti-Linguality（多语言，支持 100+ 语言）、**M**ulti-Granularity（多粒度，最长支持 8192 token 输入）、**M**ulti-Functionality（多功能，同一个模型能同时输出三种向量）：
> - **Dense**（稠密向量）：用于语义检索，我用的就是这个（1024 维）；
> - **Sparse**（稀疏向量）：类似学习型 BM25，做词级精确匹配；
> - **ColBERT / Multi-Vector**（多向量）：token 级交互，精度最高。
> **诚实补充**：bge-m3 虽然支持这三种向量，但我项目里**只用 Dense**——Sparse 和 ColBERT 我没启用，这是后续可以挖潜的方向（比如 Dense + Sparse 混合检索可能替代我现在 KNN + BM25 的方案）。

**Q4.5: bge-reranker-v2-m3 是什么架构？为什么用它做精排？**
> bge-reranker-v2-m3 是 BAAI 出品的 **XLM-RoBERTa（large）架构的 Cross-Encoder**，支持多语言。它的工作方式是把 `[query, document]` 拼成序列输入，经过 Transformer 编码后输出一个标量相关性分数（logits 过 sigmoid）。
> 用它是因为：① 多语言，中英文都强；② 开源可本地部署（我跑在 HuggingFace 的 TEI 服务里）；③ 和 bge-m3 同系列，配套效果好。
> **一个细节**：模型名不在我的 Java 代码里——TEI 服务启动时通过 `--model-id` 参数加载模型，我的 RerankerClient 只是调 TEI 的 `/rerank` 接口发 `{query, texts, top_n}`，TEI 内部用加载好的模型算分返回 `{results: [{index, relevance_score}]}`。这样模型可热替换，不用改代码。

**Q5: 为什么用 Elasticsearch 做向量库，不用 Milvus / FAISS？**
> 三点考虑：① **统一存储**：我同时需要向量检索（KNN）和全文检索（BM25），ES 一个引擎**同时提供这两种能力**（不用像 Milvus+ES 那样搭两套），Milvus 只能做向量，BM25 要另外搭；② **运维成本**：少一个组件少一份运维；③ **生态成熟**：ES 的过滤（权限过滤）、聚合、索引管理都很成熟。
> **要注意澄清**：ES 8.x 虽然支持单查询里的 knn + bool 混合检索，**但我没用那个原生 API**，而是发了两个独立的 `search` 请求（一个 KNN、一个 BM25），再在 Java 端用 RRF 融合。这样更灵活——能自定义融合算法、分别给两路加权限 filter，代价是两次 ES 往返。
> **诚实补充**：① 纯向量场景、数据量极大（亿级）时 Milvus 专门的向量库性能更好，我的场景是百万级 chunk，ES 够用；② FAISS 是库不是服务，没有增删改查和持久化，不适合做主存储；③ 我的 KNN 查询里 `num_candidates` 设成和 `k` 相等，这是个已知可优化点——ES 官方建议 `num_candidates` 设成 `k` 的几倍来扩大 HNSW 候选池提高召回精度，我后续会调。

**Q6: 你的 chunk 怎么切的？为什么这么切？**
> 我按"段落→句子→词"三级递进切：优先按段落（双换行）切，单段落超 512 字符就按句子边界切（中英文标点正则），单句仍超长就用 HanLP 分词按词切。chunk 大小 512 字符。
> 三级递进的好处是尽量在**语义边界**切，而不是硬字符切，减少语义割裂。
> **诚实补充不足**：① 我现在没有 overlap（重叠），跨 chunk 的信息会丢失——比如一个论点被切成两半。优化方向是加 10-20% overlap，或者用父子文档（小块召回，大块喂 LLM）。② 我按字符数切而不是 token 数，中英文混排时 token 数不均匀，可以用 tokenizer 统一。

**Q7: 怎么评估检索效果？Hit@5、MRR 是什么？**
> Hit@5：前 5 个召回结果里是否至少包含 1 个相关 chunk（命中=1，未命中=0），对所有测试 query 求平均。
> MRR（Mean Reciprocal Rank）：第一个相关结果排名的倒数（1/rank），比如相关结果排第 1 得 1 分，排第 2 得 0.5，对所有 query 求平均。MRR 比 Hit@5 更严格，它要求相关结果**排在前面**，不只是"被召回"。
> 我设计了评测方案：构建标注数据集（query + 相关 chunk 标签），按难度分组（easy/medium/hard），对比单路 BM25 / 单路 KNN / 混合检索三种策略的 Hit@5 和 MRR。
> **诚实补充**：方案设计完了，标注数据集和评测脚本还在完善中，目前跑的是小样本验证，完整 50 组数据集还在准备。

**Q8: 如果用户反馈检索结果不准，你怎么排查？**
> 分层排查：
> 1. **召回阶段**：先看相关文档有没有被召回（Hit@K）。没召回——可能是 chunk 切分把答案切碎了，或者 embedding 没编码对，或者 query 太口语化（要做 query 改写）。
> 2. **排序阶段**：召回了但排得靠后——RRF 权重或 rerank 没生效，检查 reranker 服务是否正常。
> 3. **生成阶段**：检索对了但回答不对——prompt 没约束好，或者上下文被噪声淹没。
> 具体手段：把 query 和召回结果打日志，人工看 top10 召回质量；调 chunk 大小和 overlap；给 rerank 更大候选池。

**Q9: 你提到混合检索比单路 BM25 提升，为什么向量检索+BM25 一定比单路好？**
> 不是"一定"，是"互补"。BM25 的盲区：query 用"怎么提高销售额"，文档写"营收增长策略"——没有词重叠，BM25 召回不到，但向量能抓到语义。向量检索的盲区：用户搜"张三"这个人名，向量可能召回语义相近的"李四"，但 BM25 能精确匹配。混合检索 + RRF 让两者投票，重复命中的文档（两路都觉得相关）排前面，单一命中的也有机会保留。

### 模块 B：上下文异步压缩（简历最强亮点，深度最够）

#### 你必须背熟的关键数字

| 配置项 | 值 |
|---|---|
| 软阈值 | 20000 token |
| 硬阈值 | 50000 token |
| 保留轮数 | 最近 6 轮（12 条消息） |
| 压缩方式 | CompletableFuture 异步 + LLM 摘要 |
| 原子性保障 | Redis Lua 脚本 |
| token 计数 | jtokkit（CL100K_BASE 编码） |

#### 面试官会问的问题

**Q1: 为什么要做上下文压缩？直接全发给 LLM 不行吗？**
> 两个问题：① **token 上限**：LLM 上下文窗口有限（即使支持 128K），对话越长每次请求的 input token 越多，成本线性上升，而且可能超限报错；② **延迟和效果**：上下文太长，LLM 的注意力会被稀释，反而回答质量下降（lost in the middle 现象），TTFT 也会变高。所以需要把早期对话压缩成摘要，只保留近期完整对话 + 摘要。

**Q2: 你说的"软硬双阈值"是什么意思？为什么不一个阈值？**
> 软阈值是**预警线**，触发**异步**压缩——不影响用户当前请求，后台慢慢压缩；硬阈值是**红线**，必须**同步**立即截断，因为 token 已经接近 LLM 上下文上限，下一次请求就可能超限报错，异步根本来不及。
> 两者维度不同：软阈值看"消息条数 OR token"（任一满足），硬阈值只看 token——因为只有 token 才直接决定会不会爆上下文窗口，消息条数反映不了长文本消息的情况。

**Q3: 你简历写的"竞态数据覆盖问题"具体是什么？（这是核心追问）**
> 场景是这样的：压缩是**异步**的，压缩线程从 Redis 读到 N 条历史作为快照，开始调 LLM 算摘要（这个过程要几秒）；就在这几秒内，用户又发了新消息，请求线程把 N+2 条新历史写回 Redis；压缩线程算完摘要后，基于它**之前读的 N 条旧快照**写回 Redis——**覆盖掉了用户新写入的 2 条消息**。这就是典型的"丢失更新"（lost update）。
> 用户会观察到：我刚发的消息和 AI 的回复，刷新一下就没了。

**Q4: 那你怎么解决的？**
> 用 Redis Lua 脚本把整个"读→删中间段→插摘要→写回"收进**一个原子操作**。Redis 是单线程模型，执行 Lua 脚本期间，任何其他命令（包括用户写新消息）都无法插入。
> 这样一来，用户的写要么在 Lua 脚本执行**之前**完成（此时压缩脚本读到的是 N+2 条，新消息进入"保留段"被保留），要么在 Lua 脚本**之后**完成（新消息写在已经压缩完的数组上）。不存在"压缩线程的读和写夹住用户写"的时间窗口。
> 脚本内部还做了二次校验：如果执行期间数据变化导致切分点越界，直接放弃操作不动数据，做兜底保护。

**Q5: 为什么用 Lua 脚本，不用 Redis 分布式锁（Redisson）？**
> Lua 脚本更轻量。分布式锁要处理锁等待、锁超时、死锁、误释放（比如 A 的锁被 B 释放）这些复杂问题，而且有性能开销。Lua 脚本利用 Redis 单线程特性，天然串行原子，不需要额外的锁协调。对于"读改写带条件判断"这种复合操作，Lua 是最佳选择——因为 Redis 事务（MULTI/EXEC）不支持中间结果的条件判断。

**Q6: 为什么是"异步压缩"而不是"同步压缩"？**
> 用户体验。压缩要调 LLM 生成摘要，耗时几秒。如果同步做，用户每发一条消息（达到阈值时）就要等几秒才收到 AI 回复，TTFT 会飙升。异步压缩让压缩在后台跑，用户当前的对话请求不受影响，正常返回。代价是异步带来的并发竞态，我用 Lua 脚本解决了。

**Q7: 压缩后的摘要怎么生成？会不会越压越失真？**
> 这是个好问题。如果每次压缩都把"已有摘要 + 新消息"一起喂给 LLM，第二次压缩的输入里就含第一次的摘要，**摘要被反复浓缩，信息逐级衰减**——这就是"摘要的摘要"问题。
> 我用**增量压缩**解决：找到上一轮的摘要作为边界，只对摘要之后的**新消息**生成独立摘要，旧摘要原样保留。这样每个摘要只描述自己那一段对话，不会反复浓缩。
> **关键实现细节（被追问"LLM 会不会不按格式输出摘要标记导致找不到边界"时要这么答）**：摘要的边界标记 `[历史摘要]` **不是 LLM 输出的，是我在 Java 代码里拼接到摘要内容开头的**——LLM 只负责生成摘要正文，代码拿到正文后在前面加 `[历史摘要] ` 前缀存进历史。所以**不存在"LLM 不按格式输出标记"的风险**，标记的拼接和识别完全在代码控制下。LLM 唯一可能出的问题是返回空摘要，代码有 `isBlank()` 兜底直接放弃这次压缩。
> 上一轮摘要的位置是通过遍历历史消息、找 content 以 `[历史摘要]` 开头的那条来定位的，用前缀匹配（`startsWith`）。

**Q8: 压缩后的数据存哪？原始对话还在吗？具体怎么存的？**
> **职责分离**：Redis 走热路径（压缩，喂 LLM），MySQL 走冷路径（归档，展示）。
> - **Redis 侧**：key 是 `conversation:{conversationId}`（conversationId 是 UUID），value 是 JSON 字符串（消息数组的序列化，每条是 `{role, content, timestamp}`），**TTL 7 天**。Redis 里存的是压缩后的（摘要 + 近期对话），因为要控制 token。
> - **MySQL 侧**：`conversations` 表，`messages` 字段是 TEXT 类型存 JSON（和 Redis 同格式），保留的是**压缩前的完整原始对话**。前端展示历史时从 MySQL 读，用户看到的是真实对话不是摘要。每轮对话完成后会同步写一次 MySQL（压缩触发前先同步，保证原始数据落盘）。
> - **缓存层关系**：切换会话时会把 MySQL 的历史重新灌回 Redis，所以 Redis 本质是 MySQL 的缓存层，不是独立存储。
> 这个"Redis 压缩 / MySQL 不压缩"的不一致是**有意设计**，不是 bug——Redis 是给 LLM 算 token 的工作集，MySQL 是给用户看的归档集。

**Q9: 怎么计算 token 数？准不准？**
> 用 jtokkit 库的 CL100K_BASE 编码（GPT-3.5/4 同款 tokenizer），对每条消息的 role+content 精确 countTokens 再求和，替代了之前"字符数/2"的粗估。
> **诚实补充**：CL100K 对中文大概 1-2 token/字，比 length/2 准；但 GLM 用的是自己的 tokenizer，CL100K 是近似——所以我把硬阈值设得比较保守（50000），留足余量，宁可估高不可估低（估低会爆窗口）。

### 模块 C：Agentic RAG / Function Calling（简历"管线设计"那条）

#### 面试官会问的问题

**Q1: 什么是 Agentic RAG？它和普通 RAG 有什么区别？**
> 普通（Naive）RAG 对**每条**用户消息**无条件检索**：query 编码 → 向量+关键词召回 → 把结果塞进 prompt → 生成。问题是：通用问题（"你好""算个 1+1"）也要白做一遍检索，浪费延迟，而且检索来的无关内容反而干扰生成。
> Agentic RAG 把"是否检索"这个决策交给 LLM 用 Function Calling 自主完成：通用问题直接 LLM 回答（省掉检索），知识库问题才触发检索。本质是把"路由"这一步从硬编码规则，上移到 LLM 的语义理解。

**Q2: LLM 怎么决定要不要检索？靠什么判断？**
> 靠两点：① 我给 LLM 定义了一个工具 `search_knowledge_base`，在工具的 description 里明确写了"通用知识、闲聊、数学计算不需要搜索"；② system prompt 里有规则引导"如果问题属于通用知识，直接用你的知识回答"。
> 这是 prompt 引导，不是硬规则，所以会有误判——比如"这个产品今年涨了多少"可能被误判成通用问题跳过检索。优化方向是加 few-shot 例子校准，或者前置一个轻量意图分类器。

**Q3: 你的 Function Calling 具体怎么实现的？讲讲流程。**
> 两阶段：
> 第一阶段——带工具定义调用 LLM，让它决策。如果它决定要检索，返回的是 tool_calls（带搜索 query）；如果不要，直接返回回答内容。
> 第二阶段——如果第一阶段触发了工具调用，我用 LLM 生成的 query 去执行混合检索，把检索结果作为一条 tool 角色的消息追加进上下文，再调一次 LLM（这次不带工具）让它基于结果生成最终回答。
> 一个关键点：如果 LLM 决定要检索，第一阶段它**不会输出任何文本**，前端不会收到半截话；只有第二阶段才流式吐字，保证用户体验连贯。

**Q4: 用的是哪个 LLM？为什么？**
> 选型逻辑：国产模型，中文效果好 + 有免费额度适合个人项目 + 走 OpenAI 兼容协议，切换其他模型成本低。
> **关于具体是哪个模型，要讲清三个 profile 的区别（代码里的类名叫 DeepSeekClient，会误导人）**：
> - 默认配置（`application.yml`，`mvn spring-boot:run` 不带 profile 时加载）：指向**智谱 GLM-5**（`open.bigmodel.cn`）；
> - dev / docker profile：切换到 **DeepSeek**（`api.deepseek.com`）；
> - README 写的"DeepSeek"对应的是 dev/docker profile。
> 所以最稳妥的回答："默认跑的是智谱 GLM-5，通过 OpenAI 兼容 API 调用；架构上模型是可插拔的，dev 和 docker 环境切到 DeepSeek，client 类名叫 DeepSeekClient 是历史命名。"
> **⚠️ 重要提醒**：配置文件里有**明文 API key**，面试如果演示项目，**千万别展示配置文件原文**，脱敏后再展示。

**Q5: 流式输出怎么做的？为什么用 WebSocket 不用 SSE？**
> 用 WebSocket。LLM API 返回的是 SSE 流（每个 token 一个 delta），我后端用 WebClient 接收后透传给前端，前端用 WebSocket 接收。
> WebSocket 比 SSE 的优势是双向——比如"停止生成"这个功能，前端要给后端发指令，SSE 是单向（服务器→客户端），要再开一条 HTTP 通道，WebSocket 一条连接搞定。代价是连接管理复杂（心跳、重连），我用前端的 autoReconnect 处理。
> **被追问"停止生成怎么实现的"**：我做的是**软停止**——前端发一个带内部令牌的 stop 指令，后端在一个会话级的 `ConcurrentHashMap` 里把这个会话标记为"已停止"，后续每次要给前端转发 LLM 的 chunk 前，先查这个标志位，是 true 就跳过不转发。
> **诚实补充不足**：这只是"不再转发给前端"，**上游 LLM 的流并没有被真正 cancel**，LLM 仍在生成并消耗 token。生产化应该用 WebFlux 的 Flux 取消或 disposable.dispose() 真正中断上游请求，省掉这部分无效开销。标志位的清理我是用裸线程延时 2 秒清除，生产该换成 ScheduledExecutor。

**Q6: 知识库问答场景下，Agentic 会不会反而更慢？**
> 会，这是我前面提到的 trade-off。知识库问答 Agentic 要**两次** LLM 调用（先判断检索，再生成），比 naive 的"检索一次+生成一次"多一次 LLM 往返，TTFT 会高一些。
> 但收益是：通用问答场景省掉了检索开销，而且整体路由更智能。如果知识库问答占比高，可以优化——比如把"判断是否检索"用一个更小的、更快的模型做，主模型只负责生成。

### 模块 D：Kafka 异步管线 + 容错（简历"架构解耦"那条）

#### 面试官会问的问题

**Q1: 为什么用 Kafka？文档处理为什么要异步？**
> 文档解析（尤其 MinerU 解析 PDF）和向量化（调 embedding 模型）都很慢，大文档可能几十秒甚至几分钟。如果同步处理，用户上传后 HTTP 请求一直阻塞，体验很差，而且并发几个大文件就把 Tomcat 线程池占满。
> 用 Kafka 异步化：上传接口收到文件立即发一条消息就返回（前端显示"解析中"），消费者在后台慢慢处理，处理完更新状态。这样上传请求快速返回，且能削峰填谷。

**Q2: 消息处理失败了怎么办？死信队列是什么？**
> 我用了 Spring Kafka 的 `DefaultErrorHandler`，配置了**固定退避重试**：失败后隔 3 秒重试，最多重试 4 次（加首次共 5 次尝试）。如果 5 次都失败，消息会被 `DeadLetterPublishingRecoverer` 发送到**死信队列**（DLQ）——一个专门的 topic 存放处理失败的消息。
> 死信队列的意义：失败的消息不会丢，也不会一直卡住消费线程阻塞后续消息。运维可以监控 DLQ，人工排查失败原因后重新处理。
> **诚实补充**：重试用固定退避适合瞬时故障（网络抖动）；如果是解析器对某个文件的固有 bug（比如 PDF 格式损坏），重试再多次也是失败，这种就该快速失败进 DLQ。

**Q3: Kafka 怎么保证消息不丢？**
> 三端保证：
> - **生产端**：acks=all（所有副本都确认才认为成功）+ 幂等生产者（防止网络重试导致重复）+ 事务（保证多条消息原子发送）。
> - **Broker**：靠多副本机制，配置合适的 replication.factor 和 min.insync.replicas。
> - **消费端**：处理成功才提交 offset，处理失败走重试+DLQ，不会因为单条消息异常阻塞整个消费。
> **诚实补充**：我目前的 offset 提交用的是默认方式，生产环境应该改成手动提交 + 处理完再提交，更严格。

**Q4: 怎么保证消息顺序？**
> Kafka 的保证是：**单 partition 内有序，跨 partition 无序**。所以顺序保证取决于 producer 把相关消息发到同一个 partition。
> 我配置了 3 个 partition、3 个消费线程。**诚实补充**：我现在发消息没指定 key，Kafka 会轮询分区，同一用户的多个文件可能落到不同分区，跨文件顺序没保证。优化方向是用 userId 做消息 key，让同一用户的消息固定到一个分区。不过当前每个文件只发一条消息，单文件内的处理顺序（解析→分块→向量化）是在消费者内部同步保证的，不受 partition 影响。

**Q5: 消费者并发怎么设的？**
> 消费线程数和 partition 数对齐（都设 3）。因为 Kafka 的规则是：一个 partition 同一时刻只能被一个消费线程消费。如果线程数 > partition 数，多出来的线程闲置；如果 < partition 数，有的 partition 没人消费。所以设成相等最合理。如果要更高并发，就加 partition 数。

**Q6: 如果数据库写成功了但 Kafka 发送失败，怎么办？**
> **诚实回答**：这是个真实的不一致风险。我现在的 Kafka 事务只保证"Kafka 发送本身的原子性"，没有把数据库操作纳入同一个分布式事务。极端情况会出现"数据库记录了文件，但消息没发出，导致文件没被解析"。
> 严谨的解法是 **Outbox 模式**：数据库写一条"待发送消息"记录，由独立任务轮询读出来发 Kafka，发送成功后更新状态。我目前的补偿方案是业务层有个对账逻辑能发现未解析的文件。这是生产化要补强的点。

### 模块 E：MinerU + 双引擎降级（JD 明确要求"MinerU 经验"，必问）

#### MinerU 必须掌握的知识（JD 第一条就是文档处理，这是必考点）

**MinerU 是什么**：上海人工智能实验室（OpenDataLab）开源的 PDF 解析工具，把 PDF 精确转 Markdown，擅长学术论文、教材、报告等复杂版面（公式、表格、多栏）。

**核心处理管线（5 阶段，必须能讲）**：
1. **版面检测**：基于深度学习目标检测模型（YOLO/RT-DETR 类），识别正文、标题、图、表、公式块、页眉页脚等区域。
2. **公式识别**：对公式区域用 Vision Encoder + Transformer Decoder 模型转 LaTeX 代码。
3. **表格识别**：重建表格行列结构，输出 HTML/Markdown 表格。
4. **OCR 文字识别**：扫描版/图片型 PDF 用 OCR（PaddleOCR）；原生数字 PDF 直接从文本层提取。
5. **阅读顺序排列**：按阅读顺序重排各区域（处理多栏论文），输出结构化 Markdown。

**MinerU vs Tika 对比（你的降级逻辑基础）**：
| 维度 | MinerU | Apache Tika |
|---|---|---|
| 复杂版面（多栏、图表混排） | ✅ 深度学习版面分析 | ❌ 线性提取，版面乱 |
| 公式/表格 | ✅ 专门模型 | ❌ 丢失或乱码 |
| 速度 | 慢（需 GPU） | 快（CPU 毫秒级） |
| 依赖 | 重（GPU + 模型） | 轻（纯 Java） |
| 输出 | Markdown（LLM 友好） | 纯文本 |

#### 面试官会问的问题

**Q1: 你用 MinerU 做什么？为什么选它？**
> 用来解析 PDF、Word 这些复杂版面文档，提取出结构化的文本给 RAG 系统切块向量化。
> 选 MinerU 是因为它对**复杂版面**的处理远超传统工具——能正确识别多栏论文的阅读顺序，能识别公式转成 LaTeX，能识别表格结构。传统工具（比如 Tika）对 PDF 是线性提取，多栏论文会把左右栏的文字交错混在一起，公式表格直接丢失。企业知识库里大量是报告、论文这类文档，MinerU 的版面分析能力很关键。

**Q2: MinerU 的原理是什么？它怎么识别版面的？**
> 核心是深度学习版面分析模型，基于目标检测架构（类似 YOLO/RT-DETR），在海量文档版面数据上训练。它把每一页当成一张图，检测出各个区域的类型和位置（正文、标题、图、表、公式块），然后对公式区域用专门的识别模型转 LaTeX，对表格区域重建行列结构，最后按阅读顺序重排，输出 Markdown。
> 相比传统基于规则（PDF 的文本坐标、字体大小）的解析，深度学习模型能理解版面语义，比如能区分"侧边栏注释"和"正文"。

**Q3: MinerU 和 Tika 你怎么选的？降级逻辑是什么？**
> 我设计成 MinerU 优先、Tika 兜底的双引擎。每次解析前先检查 MinerU 服务健康（调它的 /health 接口，5 秒超时），可用就用 MinerU；不可用（GPU 故障、服务挂了）就自动降级到 Tika，保证解析链路不中断。
> **设计思想**：MinerU 效果好但重（依赖 GPU），Tika 效果差但轻量稳定。主路径用最好的工具，降级路径保证可用性。企业场景下可用性比单次效果更重要。

**Q3.5: 你说支持多格式文档，具体支持哪些格式？不同格式解析策略有什么不同？**
> 简历写"多格式文档"，实际有三路分流，按优先级：
> 1. **MinerU 路径**（深度学习版面分析）：PDF、Word（doc/docx）、PPT（ppt/pptx）、Excel（xls/xlsx）、图片（png/jpg/bmp/tiff）——这些是有复杂版面的二进制文档，MinerU 转 Markdown 再切块；
> 2. **纯文本直读路径**（不过任何解析器）：txt、md、csv、json、xml、html，**以及代码文件**（java、py、js、ts、cpp、sql、yaml 等）——直接 UTF-8 读取后切块。代码文件走这条路径，对"代码知识库"场景有用；
> 3. **Tika 兜底路径**：MinerU 不支持但 Tika 支持的（rtf、odt、ods、epub 等），用 Tika 流式解析，带父子文档切块防 OOM。
> 三条路径**复用同一个切块逻辑**（段落→句子→词三级递进），只是前置的"文本提取"方式不同。这样扩展新格式只要加一个提取器，切块和后续流程不用动。

**Q4: 解析完了怎么切块？MinerU 输出的是什么？**
> MinerU 输出 Markdown，我拿 Markdown 文本做切块。切块按"段落→句子→词"三级递进：先按段落切，超长的段落按句子边界切，仍超长的句子用分词器按词切，目标 chunk 大小 512 字符。
> 为什么从 Markdown 切而不是从原始 PDF 坐标切：Markdown 已经是结构化文本，标题层级清晰，切块时能利用这些结构信息。

**Q5: 如果 MinerU 解析错了（比如公式识别错）怎么办？**
> **诚实回答**：MinerU 对复杂公式表格确实有误差，这是深度学习模型的固有局限。我的应对：① 切块后保留原始文档，用户可对照；② 有降级路径，极端情况退到 Tika；③ 长期靠构建评测集 + 人工标注持续优化。生产场景还需要一个人工校验环节。完全依赖自动解析不够，关键是建立"解析质量监控 + 人工反馈闭环"。

### 模块 F：大文件分片上传（简历"大文件上传"那条，之前没覆盖到）

#### 面试官会问的问题

**Q1: 大文件上传你为什么用分片？整体思路是什么？**
> 大文件（几百 MB 到 GB 级）直接上传有三个问题：① HTTP 请求超时；② 网络抖动断了就得从头传；③ 服务器内存扛不住。所以用分片上传：前端把文件切成固定大小的分片（5MB），逐个上传，全部传完后通知后端合并。
> 我用 MinIO 做对象存储 + Redis Bitmap 记录分片状态。每个分片**直接流式传到 MinIO**（不进应用服务器内存），合并也用 MinIO 的服务端合并（字节流不过应用服务器），这样应用服务器内存占用和文件大小解耦。

**Q2: Redis Bitmap 怎么记录分片状态？为什么用 Bitmap？**
> 每个分片对应 Bitmap 里的一个 bit 位——分片 index 对应 bit offset，传了就置 1，没传就是 0。一个文件的所有分片状态用一个 Bitmap 存，key 是 `upload:用户ID:文件MD5`。
> 用 Bitmap 是因为**极致省内存**：1 bit 表示一个分片。1 万个分片（约 50GB 文件）只要 1.25KB。如果用 Set 或 List 存分片索引，要几十 KB，还有序列化开销。Bitmap 是记录"大量布尔状态"的最佳数据结构。
> **诚实补充（被问"为什么 key 里带 userId"或"同一个人传两次同一文件会怎样"）**：key 带 userId 主要是为了多用户隔离。但有个已知局限——**同一个用户重复上传同一个文件（同 MD5）时 key 会复用**，断点续传会读到上次的 Bitmap 状态，可能误判"这些分片传过了"直接跳过，实际 MinIO 那边分片可能已不在（被上次合并清理掉了）。严格做法是 key 再加一个 uploadId 或时间戳保证每次上传独立，目前靠 24 小时 TTL 兜底（超时 Bitmap 自动失效，会从头传）。这是个可以优化的点。

**Q3: 断点续传怎么实现的？**
> 上传过程中断了（网络故障、刷新页面），用户重新选择同一个文件后，前端先调一个 status 接口，后端读 Bitmap 返回**已上传的分片索引列表**，前端拿到后跳过这些分片，只传缺失的。
> 这里有个优化点：后端不是循环 GETBIT 一个个查，而是**一次性把整个 Bitmap 读出来**，在本地按位解析出哪些是 1，减少 Redis 的 RTT 次数。Bitmap 是大端位序，解析时要注意位顺序。
> 文件一致性靠 MD5：重新选的文件要重新算 MD5，和原来的对比一致才续传，防止用户换了文件。

**Q4: 分片合并怎么做的？**
> 全部分片传完后，前端发 merge 请求，后端用 MinIO 的 `composeObject` 做**服务端合并**——直接在 MinIO 集群内部把多个分片对象拼接成一个完整对象，**字节流不经过应用服务器**。合并完删掉分片、删掉 Bitmap。
> 服务端合并的好处：不占用应用服务器内存和带宽，大文件合并也很快。分片大小设 5MB 是卡 MinIO composeObject 的最小分片限制。

**Q5: 怎么判断全部分片都传完了？**
> 三层校验：前端看已传分片数等于总分片数就触发 merge；后端 merge 前再从 Bitmap 统计已传数量，不够就拒绝；merge 内部还从数据库分片表 count 一次。三层校验防止并发或状态不一致导致提前合并。

**Q6: 高并发下会不会有问题？（简历写了"保障高并发下的传输稳定性"）**
> 分片上传的幂等性做得扎实：同一个分片重复上传，Bitmap 已置位就跳过，还有数据库记录和对象存在性二次校验，所以网络重传不会出问题。
> **诚实补充短板**：merge 阶段我目前没有加分布式锁，如果用户狂点合并按钮，可能触发两次合并（MinIO 端覆盖，第二次删分片会失败但被吞掉）。生产化应该加分布式锁或前端防重复点击。另外，传了一半用户不传了的分片，Redis Bitmap 有 24 小时 TTL 自动清理，但 MinIO 里的分片对象没有定时清理任务，长期会占存储——这也是要补的，加个定时任务扫描清理。

### 模块 G：多租户隔离 / 权限过滤（简历"私有化知识库""多租户"那条，之前漏覆盖）

> ⚠️ 这块是简历白纸黑字写的功能，但准备文档之前一条 Q&A 都没有——**面试官看到"私有化""多租户"几乎必问**，是这次审查补的最高优先级内容。

#### 核心设计：两层隔离

**第一层：HTTP 请求层（资源级 ACL）**
- 一个 `OncePerRequestFilter`，基于文档上的 `orgTag` 字段做访问控制。
- 三级权限判定：① 资源拥有者（userId 匹配）；② 公开资源（`public=true`）；③ 同组织标签成员（orgTag 在用户的有效标签集合里）。
- 特殊规则：`ADMIN` 角色全放行；`PRIVATE_` 前缀的标签只允许拥有者访问；`DEFAULT` 组织标签所有用户默认可见（强制塞进每个用户的有效标签）。

**第二层：检索层（ES filter 子句）—— 这是最该讲的点**

**Q1: 检索时怎么保证用户只搜到自己有权限的文档？是召回后过滤还是召回前过滤？**
> **召回前过滤**。我在构建 KNN 和 BM25 两个查询时，把同一个权限过滤条件挂到 ES 的 `filter` 子句上（`permissionFilter`），它是三条 `should`（OR 关系）：
> ① 文档 userId 等于当前用户（自己的文档）；
> ② 文档 public 等于 true（公开文档）；
> ③ 文档 orgTag 在用户的有效组织标签集合里（所属组织文档）。
> 关键是它挂在 `filter` 而不是 `must`，且**同时挂在 KNN 的 `.filter()` 和 BM25 的 bool `.filter()` 上**，所以两路召回在 ES 端就已经被权限裁剪——无权限的文档根本不会进入候选池，不是召回一大堆再在 Java 端筛。这避免了"召回到敏感文档但被排序筛掉"的安全隐患（召回过的就可能进日志）。

**Q2: filter 和 must 有什么区别？为什么权限用 filter？**
> `must` 参与相关性打分（影响 BM25 score），`filter` 只做"要/不要"的布尔判定，不参与打分。
> 权限判定是**硬性条件**（要么有权限要么没有，和相关性无关），用 `filter` 有两个好处：① 不污染相关性分数（文档不会因为"权限匹配"而得分变高）；② ES 会对 filter 做缓存，性能比 must 好。

**Q3: 组织标签怎么支持层级？比如子部门的人能看父部门的文档吗？**
> 支持。我做了**标签层级继承**：查询用户的"有效组织标签"时，不只取他直接所属的标签，还会**递归收集所有父级标签**。比如用户属于"华东-上海"标签，他有效标签集合里会有"华东""上海"两个，所以能检索到标记为"华东"（父组织）的文档。
> 这个递归收集的结果用 Redis 缓存（24 小时 TTL），避免每次查询都递归算。每个用户默认还会被塞入一个 `DEFAULT` 标签，保证公共默认内容所有人可见。

**Q4: 公开文档和私有文档怎么区分？**
> 两套机制并存：
> ① **公开标志**：文档有个 `public` 布尔字段，true 就是所有人可见（挂在 permissionFilter 的第二条 should 里）；
> ② **私有标签前缀**：`PRIVATE_` 开头的 orgTag 表示私密组织，只有拥有者能访问（在 HTTP filter 层做特殊拦截）。
> 用户上传时可以选"公开"或"绑定到某个组织"，对应这两个字段的设置。

## 四、简历技能栏的追问（面试官看到技能点会随机问）

### MCP 协议（见第一节风险 4，核心是别吹过头）

**被问"MCP 是什么"**：
> MCP（Model Context Protocol）是 Anthropic 2024 年底推出的开放协议，目的是**标准化 LLM 应用与外部数据源/工具的通信**，被称为"AI 应用的 USB-C 接口"。
> 它定义了三种能力：**Tools**（可执行函数，LLM 通过 Function Calling 触发）、**Resources**（只读数据源）、**Prompts**（预定义提示词模板）。
> 两种传输方式：**stdio**（本地，Client 启动 Server 作为子进程，通过标准输入输出交换 JSON-RPC 消息）；**Streamable HTTP**（远程，2025 年 3 月的新版协议，替代了早期的 SSE 双端点模式）。
> 核心价值：让一个工具 Server（比如查数据库、调企业 API）能被任何支持 MCP 的 Host（Claude Desktop、Cursor）复用，不用每个 LLM 应用各自集成。

### Skill 机制

**被问"Skill 是什么"**：
> Skill 是 Anthropic Claude 的"技能"机制，把特定领域的操作流程（SOP）封装成一个 SKILL.md 文件 + 辅助脚本，LLM 加载后按流程执行复杂任务。本质是"给 LLM 的可复用操作手册"。

**Function Calling vs MCP vs Skill 的关系（高阶问题，能答出来加分）**：
> - **Function Calling**：单步原子操作，LLM 决定调哪个函数。
> - **MCP**：标准化协议，把工具/资源以标准格式暴露给任何 Host。
> - **Skill**：多步操作流程（SOP），LLM 按步骤编排多个工具调用完成复杂任务。
> 一句话：Function Calling 是原子操作，MCP 是操作的标准化传输，Skill 是操作的编排流程。

### Harness Engineering（简历写了"前沿 AI Agent 技术趋势"）

**被问"Harness Engineering 是什么"（如果面试官懂行会问）**：
> 这是 2025 年 Agent 工程的一个反思趋势。核心观点是：**不要把 Agent 的控制流全交给 LLM 用 prompt 编排**（容易跑偏、不可控、难调试），而是用**确定性的代码（harness）来编排控制流**，LLM 只在每个原子步骤里贡献能力。
> 比如一个"查订单→分析→回复"的流程，传统 multi-agent 让 LLM 自己决定下一步，harness 方式是代码固定走这三步，每步调 LLM 做具体能力（理解、分析、生成）。
> 我项目里的 Agentic RAG 其实就体现了这个思想——两阶段的控制流是我用 Java 代码确定的（先判断检索、再生成），LLM 只在每步里做语义决策，不是让 LLM 自己在一个大循环里自由发挥。

### Prompt Engineering（简历写了"熟悉 Prompt 编写"）

**被问"你的 prompt 怎么设计的"**：
> 我针对不同任务设计不同 prompt。问答场景的 system prompt 包含：角色定义（知识助手）、工具使用引导（什么情况要检索）、回答规范（先结论后展开、强制标注来源、不编造）、防幻觉约束。
> 压缩场景单独有 prompt，明确告诉 LLM"只对新对话生成摘要，不要合并旧摘要"。
> 关键经验：① prompt 要明确约束 LLM 的边界（什么时候检索、什么时候直接答）；② 防幻觉要显式写"不得编造检索结果之外的内容"+ 强制引用来源；③ 不同任务用不同 prompt，不要一个 prompt 干所有事。

## 五、通用 RAG / AI 理论（开放性深挖，考察广度）

### 高频问题

**Q: Embedding 模型和 Reranker 模型有什么区别？**
> Embedding 是 Bi-Encoder（双塔），query 和文档独立编码，能离线建索引、在线快速检索，但精度有限。Reranker 是 Cross-Encoder，query 和文档拼一起交互编码，精度高但只能在线对少量候选精排。两者是"召回"和"精排"的关系，不是替代。

**Q: 什么是幻觉（Hallucination）？怎么缓解？**
> 幻觉是 LLM 生成看起来合理但事实上错误的内容。RAG 本身就是缓解幻觉的重要手段——让 LLM 基于检索到的真实文档作答。其他手段：prompt 约束（"基于给定内容回答，不知道就说不知道"）、强制引用来源、温度调低、后处理做事实核查。

**Q: 什么是 Lost in the Middle 现象？**
> LLM 对长上下文，注意力在**开头和结尾**强，**中间**弱。所以检索结果塞在 prompt 中间位置反而容易被忽略。应对：把最相关的文档放靠前/靠后，或限制上下文长度（这也是我做压缩的原因之一）。

**Q: 多轮对话你怎么处理的？**
> 我把对话历史存 Redis（热路径）+ MySQL（冷路径归档）。每次请求带上历史上下文给 LLM。对话过长时触发压缩，把早期对话摘要成摘要消息，只保留近期完整对话 + 摘要，控制 token。

**Q: 如果数据量从百万级涨到亿级，你的架构要怎么改？**
> 几个方向：① **检索**：ES 可能扛不住，考虑 Milvus 专门的向量库 + ES 只做 BM25，或者用 ES 的数据分片；② **Embedding**：离线批量向量化，消息队列削峰；③ **存储**：chunk 冷热分离，热数据 ES，冷数据归档；④ **缓存**：query embedding 结果和热门检索结果缓存（Redis）；⑤ **多级检索**：先粗召回到大池子，再精排。

**Q: 你了解 LangChain / LlamaIndex 吗？为什么不用框架自己写？**
> 了解原理。不用框架的原因：① 我的项目要深度定制（混合检索的 RRF 融合、压缩的竞态处理），框架的抽象反而碍事；② 自己写能完全掌控，便于排查和优化；③ 学习深度，手写一遍 RAG 全流程对理解远超调框架 API。
> **但如果快速搭原型**，我会用 LlamaIndex，它对 RAG 的抽象做得好。

### RAG 进阶技巧（你没用，但要能聊——展示广度）

如果被问"还有什么优化方向"，准备这几个：
- **Query 改写**：LLM 把口语化 query 改成检索友好的关键词。
- **HyDE（假设文档嵌入）**：先让 LLM 生成假设答案，用假设答案的 embedding 检索（答案和文档的语义分布更接近）。
- **Multi-Query**：生成多个改写 query，分别召回取并集。
- **Self-RAG**：LLM 自我反思检索结果够不够，不够就再检索。
- **父子文档**：小块召回（精准）、大块喂 LLM（上下文完整）。

> **话术**："目前做了两路召回+RRF+rerank，query 改写、HyDE、multi-query 是我识别的下一步方向。比如 HyDE 对口语化提问场景提升明显——先让 LLM 生成假设答案，用答案而非原 query 去检索，因为答案和文档的语义分布更接近。"

## 八、行为面 + 反问

### 准备 3 个 STAR 故事

**故事 1：遇到最难的并发 bug**
> **S**：长对话压缩功能上线后，偶发用户反馈"刚发的消息刷新就没了"。
> **T**：定位并修复这个并发问题。
> **A**：分析发现是异步压缩线程和用户实时写入的"丢失更新"——压缩线程基于旧快照算完摘要后覆盖了用户新消息。我用 Redis Lua 脚本把"读-改-写"收成原子操作解决。
> **R**：彻底消除竞态，还做了二次越界校验兜底。这让我深刻理解了异步场景下"读改写"必须考虑原子性。

**故事 2：系统效果优化**
> **S**：最初是 Naive RAG，所有问题都检索，通用问答延迟高。
> **T**：优化路由，降低通用问答延迟。
> **A**：升级成 Agentic RAG，用 Function Calling 让 LLM 自主决策是否检索。
> **R**：通用问答跳过检索，响应变快；也让我思考了 trade-off——知识库问答反而多一次 LLM 往返。

**故事 3：从 Java 到 AI 应用的转型**
> **S**：本科数字媒体，研究生转 AI，但发现 AI 应用层缺工程化人才。
> **T**：把 Java 后端能力迁移到 AI 应用工程化。
> **A**：做 ShadowRAG 时，把并发（压缩竞态）、消息队列（Kafka 容错）、缓存设计（Bitmap）这些后端经验用在 RAG 系统里。
> **R**：体会到 AI 应用的瓶颈往往不在模型，而在工程——检索准确率、系统稳定性、成本控制，都是工程问题。
