### DLT 死信队列改进方案咨询
- 用户问 DLT 无人消费怎么改、ROI 最高方案。
- 关键判断：DLT 失败多为永久性错误（presigned URL 过期/文件损坏/格式不支持/GPU OOM），自动重投对永久错误无效，临时错误已被 DefaultErrorHandler 4 次重试覆盖，故自动重投 ROI 低。
- 初版推荐 A+（DLT 消费者+errorReason+手动重投接口）。
- **用户纠正（正确）**：DLT 标准做法是"留存 bug 消息 + 告警通知运维 + 人工排查根因"，重投是低频例外不是核心。到 DLT 的多是永久错误，重投无效；当前真痛点是"静默失败无人知"。故修正：告警才是核心，重投降为可选。
- **修正后 ROI 最高方案**：DLT 消费者 → 落库(parseStatus=4 + errorReason) + 企微群机器人 webhook 告警（HTTP POST，无需连 wecom connector）。重投接口降为可选辅助（仅根因修复后人工触发）。
- 告警通道：企微群机器人 webhook 最轻量，POST qyapi.weixin.qq.com/cgi-bin/webhook/send?key=XXX，body {msgtype:text,text:{content}}。

### 知识图谱引入方案咨询
- 用户问引入图谱 ROI 最高的方式。
- 判断：全量 GraphRAG（全文档建图+社区检测+社区摘要）是 ROI 陷阱——构建贵(LLM 大量调用)、更新难(文档改了要重建)、大部分查询用不上向量检索已够。
- 图谱真正补的短板：多跳推理(A→B→C 关系链)、实体消歧(同名实体)、精确关联过滤、全局主题归纳。
- 推荐渐进路径：① 实体增强检索——用现有 HanLP 1.8.6 做 NER，实体入 ES 新字段，query 抽实体做 filter/boost，零新依赖解决消歧+精确召回。② 按需小图——仅对高频关系域(组织架构/产品谱系/合同条款)抽三元组入 Neo4j，不追求全量，解决多跳。③ Agentic 工具化——graph_query 作为第二个工具，LLM 自主决定多跳问题走图谱，对接之前 Agentic RAG 的多工具扩展点。
- 关键原则：图谱是增量补丁非重构；先实体增强(最低成本)，验证收益再上小图，最后工具化。

### Java NIO 使用情况排查
- 全量扫描 85 个 java 文件 + pom.xml + resources。
- **结论：业务代码没有真正意义上的 NIO 编程**。只用到 java.nio 包里两个"工具类"：
  - `java.nio.charset.StandardCharsets`：WebConfig(52)、EsIndexInitializer(72)、DocumentService(290/298/337)、ParseService(115/461)、DocumentController(23) — 纯 UTF-8 常量。
  - `java.nio.file.Files`：仅 `EsIndexInitializer.java:72` 一处 `Files.readAllBytes(...)` 读 es-mappings/knowledge_base.json。
- **零使用**：Channel / ByteBuffer / Selector / SelectionKey / MappedByteBuffer / AsynchronousFileChannel / 零拷贝 transferTo。全库 grep 无匹配（只命中前端 test.html 的 JS `querySelectorAll`）。
- 文件 I/O 全走传统 java.io（InputStream/BufferedReader/InputStreamReader），大文件分片上传由 MinIO SDK 的 ComposeSource 服务端合并，不经本地磁盘，所以没有用 NIO 优化的动机。
- pom.xml 无任何显式 NIO/Netty 声明；但传递依赖里 NIO 无处不在：Tomcat NioEndpoint(starter-web/websocket)、Reactor Netty(starter-webflux，WebClientConfig 建了 3 个 WebClient)、Kafka NetworkClient(nio.Selector)、ES RestClient(HttpAsyncClient)、Lettuce(Netty)、MinIO(OkHttp)。~/.m2 已确认存在 netty-buffer/transport/epoll + reactor-netty。
